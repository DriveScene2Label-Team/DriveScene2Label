# 성능 최적화 실험 기록

> **후속 결과:** G2 전체 씬·3D 회귀와 C1 통제 비교를 통과해 hybrid에 채택했다. G2 전체 시간 3.08%, C1 인덱싱 중앙값 12.69% 감소. 전체 원본 벡터·검색과 S3 복원도 검증했다. 최신 전체 사이클·CPU 스레드·중지 상태는 [2026-11-18 통합 보고서](optimization-results-2026-11-18.md)를 따른다. 아래 G1 당시의 보류 판단은 당시 기록으로 보존한다.

각 실험의 문제·가설·변경·도구 선택·조건·원시 로그·품질·판정을 함께 보존한다. 성공하지 않은 실험도 삭제하지 않는다. 시간은 UTC 원본과 KST 표시를 구분한다.

## 문제 정의

1. **자동 라벨 생성:** 기존 한 씬 executor 1,808.547초 중 검출이 1,035.422초였다. 클래스별 전처리·forward·CPU 복사의 반복을 실제 계수로 확인한다.
2. **검색 준비:** 업로드부터 인덱스 완료까지 기다린다. 최신 scheduler 수정 이후의 통합 기준선을 먼저 측정해 SQL·HTTP·추론·작업 사이 대기를 분리한다.

기존 RDS·S3와 데이터는 유지한다. 서버 이전은 코드 변경 비교 뒤의 별도 실험이다.

## 원본 분석을 적용할 때 수정한 사항

사용자 제공 원본: `DriveScene2Label 병목 분석과 최적화 선정.md` (2026-11-17 수신). 문서의 제안과 실제 코드 사실을 구분한다.

- 실제 `p_final.yaml` 검출 threshold는 **0.3**이다. 원본의 G1 표에 있는 pipeline 기본값 0.1로 바꾸지 않는다.
- `pg_stat_statements_reset()` 대신 가능하면 전후 snapshot 차분을 사용한다. 기존 DB 통계를 지우지 않는다.
- 기존 벡터 삭제 대신 새 테스트 데이터셋이나 별도 테스트 DB를 사용한다.
- 이미지 테이블/키는 문서의 예시 `image_id, model_ver`가 아니라 실제 `sample_data`와 `dataset_id, sample_data_token, model_name, preprocess`에 맞춘다.
- 클라이언트 SQL 시간에서 서버 시간을 뺀 값에는 네트워크 외에 드라이버·풀·직렬화 비용도 있다. 이를 순수 WAN RTT로 표기하지 않는다.
- CUDA event 경과시간은 해당 stream의 구간 시간이며 순수 커널 시간 합과는 다르다. kernel별 시간은 profiler 진단으로 확인한다.
- 기존 SAM 433초는 추론·복사·후처리를 포함한 총량이다. GPU/CPU 세부 분할은 추가 계측 대상이다.
- 소량 비교에서 빠르더라도 전체 씬·검색 품질 검증 전에는 운영 기본값으로 채택하지 않는다.

## 실험 폴더 규칙

- `manifest.json` / `test-conditions.json`: 커밋·이미지·입력·캐시·경로·동시 작업·실험 경계.
- `events.jsonl`: 구조화된 단계 원본. 모델 비교는 이미지/조건/반복 ID를 포함.
- `resources.jsonl`: GPU·Docker·메모리·IO 관측.
- `client-report.json` 또는 `summary.json`: 완료 여부·건수·클라이언트 경과시간.
- `report.md`: 문제, 해결 후보, 도구 선택 이유, 실제 결과, 비교 가능한 범위, 판정.
- 진단 실행은 `diagnostic=true`로 구분. hook/강제 동기화/프로파일러 여부 명시.
- 테스트 명령·stdout/stderr·실패 원인 유형과 수정 후 재실행을 별도 보존. 비밀번호·쿠키·토큰·환경변수 전체를 저장하지 않음.

## 비교 원칙

동일 입력·모델·전처리·threshold·dtype·스레드·캐시 조건을 고정한다. 첫 호출과 warm 구간을 분리하고 warm 비교는 최소 3회 반복한다. 결과 수만 맞는 것을 품질 통과로 간주하지 않는다. 전후 출력 비교, 클래스별 누락, 벡터 차이와 검색 순위를 확인한다. 전체 경로 검증이 남으면 판정은 `보류`로 남긴다.

미실행 목표값, 코드에서 예상한 호출 수, 실제 관측은 각각 표시한다. 서로 다른 경로인 과거 865초와 단독 185초를 나눠 개선율을 만들지 않는다.

## C0 결과로 정한 두 번째 케이스

CLIP / CLIP_STAGE 로그 각각 2,424건, 이미지 ID 중복 0, 수집 오류·실패 0. 이미지별 총 시간 합 266.322초, AI 요청·검증 197.754초, 저장 27.537초, source/exists/cache 등 미분리 41.031초이다. 이미지별 총 시간 중 AI 요청 바깥 비중 25.7%이므로 CLIP DB 경로를 유지한다. 이 25.7%를 순수 SQL 시간이나 순수 WAN RTT로 부르지 않는다.

추정 이미지 사이 최대 공백 0.227초, 전체 구간과 이미지 처리 합의 차이 3.694초로 과거 수백 초 공백은 관측되지 않았다. 이전 실행과 조건이 달라 scheduler의 인과적 개선율은 산출하지 않는다. 기존 수정이 있는 상태에서 추가 개선 가능 구간을 측정한 기준선이다.

업로드 전송 122.875초, 서버 처리 226.091초(복사 6.200, 압축 해제 62.044, S3 보관 145.571, DB 등록 12.274). 서버 TOTAL과 하위 구간은 중첩이다. 호스트 가용 메모리 최소 173 MB도 기록되어 다음 실행의 자원 조건을 확인해야 한다.

CLIP 계측 코드는 source_ms / cache_ms / exists_ms와 CLIP_INDEX 시작·종료·양보·실패를 추가했다. 이 변경은 C0 실행 이후 작성했으므로 C0에 해당 필드가 있다고 주장하지 않는다. L0에서 backend 이미지 `sha256:b1582a2fb8e721afef0d1ffeebbf5b42b69b85735193d5648d501e66146284b3`로 반영하고 실제 SKIPPED 요청 로그의 새 필드까지 확인했다. SQL 왕복 축소·벡터/검색 품질 비교는 후속 단계이다.

L0의 첫 readiness 확인은 존재하지 않는 `/api/health`를 사용해 실패했다. 실제 Compose 경로 `/api/datasets`와 Docker health로 정정하여 정상 확인했다. 잘못된 확인 경로도 실험 폴더에 남겼으며 서비스 기동 실패로 집계하지 않는다.

계측 회귀 검증은 총 26개 통과했다(T1 6개, T2 Python 10개·Java 10개). Java 테스트가 10분 소요되어 두 차례 스레드 진단도 보존했다. 진단 시점에 Windows 공유 경로의 클래스 로딩과 테스트 파일 생성이 관측되었으며, 이 테스트 실행시간을 서비스 또는 GPU 성능으로 비교하지 않는다.

## 기록 도구와 실행 절차

1. 매번 새로운 측정 폴더를 만들고 조건·명령을 기록한다. 이미 사용한 디렉터리로 업로드/benchmark를 재실행하지 않는다.
2. CLIP 정상 경로는 `scripts/hybrid/benchmark_clip.py`, 구조화 수집은 기존 `measurement.py`, 30초 자원 샘플은 `sample_resources.py`를 사용한다. benchmark는 최종 JSON과 매 이벤트 JSONL을 따로 저장한다.
3. Grounding 비교는 `ai-server/tools/benchmark_grounding.py`를 설치된 `/opt/vespa-env/bin/python`으로 실행한다. `--mode baseline --diagnostic`은 진단, `--mode compare --frames 2 --repeats 3`은 첫 반복 비교다. `--output`은 새 디렉터리만 허용한다.
4. stdout/stderr와 exit code를 보존하고 실행 코드 사본·SHA256을 남긴다. 실패 실행도 그대로 두고 다음 시도는 새 폴더로 만든다.
5. 수집기 STOP → 프로세스 종료 확인 → CLIP 마지막 collect 순서로 확정한다. 수집기 두 개가 같은 manifest를 동시에 쓰지 않도록 한다.
6. CLIP은 `python scripts/hybrid/summarize_clip.py --directory <완료 폴더>`, Grounding은 `python scripts/hybrid/summarize_grounding.py --directory <완료 폴더>`로 원본에서 report.md와 comparison-summary.json을 생성한다.
7. 이 표에 측정 범위·성능·품질·채택/보류 이유를 추가한다. 고정 조건이 달라지면 별도 실험이며 결과를 같은 개선율로 묶지 않는다.

원본 조사 문서의 5회 warm 측정은 후속 안정성 확인 계획으로 유지한다. 이번 첫 G1은 사용자 제공 상세 계획의 최소 3회로 실행하며, 3회 결과를 5회 측정으로 표기하지 않는다.

## G1 결과와 후속 검증

| 반복 | baseline (12장, 초) | 전처리 재사용 (12장, 초) | 시간 감소 |
|---|---:|---:|---:|
| 1 | 66.254 | 57.659 | 12.97% |
| 2 | 64.603 | 56.992 | 11.78% |
| 3 | 65.377 | 57.690 | 11.76% |

예상 72개 관측이 모두 기록되었고 (조건, 반복, 이미지) 중복은 없다. 전처리 360→36회, forward는 양쪽 360회로 변경 범위가 실제 계수와 일치한다. 좌표·점수·클래스·순서를 포함한 출력은 36/36쌍 완전 일치했다. 자원 샘플 14개, 수집 오류 0, 호스트 가용 메모리 최소 1,115 MB였다.

판정은 **실험 후보 유지, 운영 채택 보류**다. 11.81%는 이 검출 소량 실험의 반복 합계 중앙값 감소이며 전체 VESPA/업로드 개선율이 아니다. 프로덕션 `_vlm_detection` 경유 전체 씬과 최종 3D 결과는 미검증이다. 다음에는 이 후보의 전체 씬 회귀를 확인하고, 클래스별 forward batching은 별도 변화로 비교한다. 병합 프롬프트는 클래스 매핑·검출 의미가 달라지므로 출력 동등 최적화로 묶지 않는다.
