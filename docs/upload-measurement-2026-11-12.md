## 임베딩과 GPU

원본 S3 보관과 DB 등록은 GPU 작업이 아니다. 등록 후 CLIP 인덱싱이 시작됐고 실제 AI `/health`의 장치는 `cuda`였다. **2,424/2,424장 COMPLETED**를 확인했다. 이 문서의 업로드 총 시간에는 임베딩이 포함되지 않는다.

16:48:58에 라벨 작업 #7(scene-0061)이 시작돼 2,208장에서 임베딩이 대기했다. 사용자가 ‘임베딩 완료 후 직접 라벨링’ 순서를 요구하여 #7의 격리된 runner에만 SIGTERM을 보냈고, 서버가 FAILED로 마감한 뒤 남은 216장이 처리됐다. 현재 취소 상태가 없어 실패로 보이며 모델의 자연 발생 실패로 분류하지 않는다. 중단 근거는 `verification-20261112/job7-manual-order-stop.json`, 임베딩 집계는 `embedding-analysis.json`에 보관했다. 첫/마지막 로그 시각 차이는 중간 대기를 포함하는 관측 구간이지 순수 추론 시간이나 무중단 성능이 아니다. AI 호출도 GPU 커널 시간과 다르다. 이미지별 전체 시간에는 AI/저장이 포함된다.

코드상 `DatasetSearchIndexService`는 한 번에 미처리 ID 최대 8개를 뽑아 **이미지별로 순차 `embed` 호출**한다. 8장 GPU batch 추론이 아니다. `DatasetSearchIndexWorker`는 작업 후 기본 **1초 fixedDelay**로 다시 실행한다. 조회·heartbeat·벡터 저장도 각 호출 사이에 존재한다. 따라서 순간 GPU 그래프가 낮아도 모델이 CPU로 실행된다고 단정할 수 없다.

VESPA와 검색 인덱싱은 로컬 scheduler를 공유한다. 사용자가 라벨 작업을 시작하면 검색 준비의 완료 경과에 대기 시간이 섞일 수 있다. index 상태 `PENDING`도 처리 중 묶음 사이에 나타날 수 있어 그 상태 하나만으로 장애를 판단하지 않는다.

이 시험에서 드러난 실행 순서 문제를 해결하기 위해 업로드 데이터셋의 임베딩 완료 전 새 라벨 요청을 거절하고 버튼을 막도록 수정·검증·배포했다. 임베딩 완료는 작업 생성 이벤트가 아니며 이후 사용자의 클릭이 필요하다. 관련 PostgreSQL 23개·브라우저 fixture 2개를 통과했다. 이후 #8(scene-1077), #9(scene-0061), #10(scene-1094), #11(scene-0103)은 사용자 요청으로 중단해 완료 성능에서 제외한다. #8 일부 구간에는 개발 빌드·테스트도 겹쳤으므로 통제된 성능 비교가 아니다. #11은 17:25 KST 중단 후 running/pending 0을 확인했다. 17시 이후 Cloudflare 전환은 이 업로드 실측과 별도다.

## 다음 비교 실험과 개선 순서

1. **같은 PC의 loopback 업로드 대조군:** 같은 파일로 경로만 바꿔 전송 단계와 조각 서비스 밖 시간을 비교한다. 이번 공개 업로드와 모델·DB·S3 조건을 기록하고 사용자 승인 없이 중복 업로드를 만들지 않는다.
2. **전송 방식:** 제한된 조각 동시성 또는 S3 직접 multipart를 비교한다. 현재 API는 연속 offset·단일 수신 위치를 검증하므로 단순히 프론트 Promise 수만 늘리면 안 된다. 재시도 멱등성·파일 일관성·재개·게이트웨이 제한을 함께 설계한다.
3. **S3 보관과 씬 가용 시점:** S3 보관 141.5초를 줄이거나 등록과 겹칠 수 있는지 검토한다. 원본 보존 실패 시 데이터셋 상태·보상·재시도 의미가 달라지므로 저장 순서만 바꾸지 않는다.
4. **CLIP 묶음 추론·DB 묶음 저장:** 작은 입력 batch와 결과 동등성·VRAM·VESPA와의 경합을 비교한다. 1초 대기는 작업 간 양보 목적이 있으므로 삭제 효과와 공정성을 함께 측정한다.
5. **RDS/SQL:** 이번 메타데이터 등록은 약 9.9초로 작았다. 실제 느린 쿼리를 특정하기 전 ORM 교체·Redis 도입을 우선하지 않는다.

이번 측정은 문제 위치를 좁힌 결과다. 위 후보의 전후 실험은 아직 하지 않았으며, 스레드 증가나 GPU 교체로 개선했다고 보고하지 않는다.
