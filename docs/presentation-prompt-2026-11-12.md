# 교수님 발표용 10장 프롬프트

아래 본문을 Claude에 그대로 전달한다. README와 [실측 보고서](upload-measurement-2026-11-12.md)를 함께 제공하면 좋다. 기준일 2026-11-12. 진행 중인 작업의 완료 시간과 확인하지 않은 요금은 만들지 않는다.

---

DriveScene2Label 캡스톤 프로젝트의 **교수님 발표 자료를 한국어로 정확히 10장** 만들어 줘. 발표 시간은 약 5~7분, 대상은 컴퓨터공학 교수님이야. 화면 한 장마다 결론형 제목, 핵심 3개 이내, 필요한 그림 또는 표 하나, 발표 대본 2~3문장으로 구성해. 기술 용어 나열보다 ‘요구사항 → 선택 → 실제 문제 → 측정 → 개선’이 이어지게 해.

프로젝트는 nuScenes 주행 데이터를 업로드하고, CLIP으로 자연어 검색하며, 사용자가 선택한 씬을 VESPA로 3D 자동 라벨링하는 웹 서비스야. 라벨을 6개 카메라·LiDAR에서 확인하고 수정·저장해. 일반 YOLO의 2D 검출만 수행하는 서비스와 구분해.

다음 순서와 사실을 사용해.

**1장. 무엇을 만드는가**
- 주행 데이터 업로드 → 씬 검색·탐색 → 선택한 씬의 3D 라벨 생성·편집.
- 의도한 사용자 순서: 업로드 후 검색 임베딩은 자동으로 완료하고, 라벨링은 사용자가 씬에서 버튼을 눌렀을 때만 실행.
- 씬 하나는 여러 키프레임이다. scene-0061은 39프레임, scene-0103은 40프레임. 전체 데이터셋을 한 번에 추론하지 않는다.

**2장. 처음에는 AWS에 실행 환경까지 배포했다**
- ECS Fargate 웹/API, 별도의 EKS + CPU EC2로 동일 이미지 배포 방식도 비교 검증했다. 두 서비스가 항상 모두 필요하다는 뜻은 아니다.
- GPU는 ECS EC2 `g6.2xlarge`, NVIDIA L4 1장, VRAM 24GB급, 8 vCPU, RAM 32GiB였다.
- RDS PostgreSQL/pgvector와 S3는 데이터를 보관했다. 이 구성은 과거 운영 이력이며 현재 EC2·ECS·EKS는 사용하지 않는다.

**3장. GPU를 빌리는 것만으로 느린 처리가 해결되지는 않았다**
- 과거 L4에서 scene-0061, 39키프레임·8class 작업: 약 22분 43초, 983개 예측 박스.
- 그중 이미지 검출·분할 약 17분 43초(약 78%), 지면 제거 약 2분 22초, DINOv2 약 1분 55초. 과거 로그의 근삿값이다.
- 한 시점 GPU 사용률 약 98%, VRAM 약 11.2/22.5GiB였다. GPU 미사용이나 L4의 코어 부족으로 원인을 확정하지 않는다. VRAM 용량은 곧 처리 속도가 아니다. 한 씬의 결과를 전체 평균으로 일반화하지 않는다.

**4장. 현재는 화면·연산·영속 저장을 나눴다**
큰 구조도 하나로 표현해:
사용자 브라우저 → Vercel React → Cloudflare Quick Tunnel → 로컬 oauth2-proxy → Spring Boot → 로컬 FastAPI/CLIP/VESPA. 11월 12일 업로드 실측은 전환 전 Microsoft 터널 경로였으므로 현재 Cloudflare의 성능으로 재사용하지 마.
- 로컬 GPU: 기존에 보유한 RTX 5060 Ti 16GB eGPU, Docker/WSL2 사용.
- Spring ↔ AWS 서울 S3: 원본 ZIP/TGZ 보관·복원.
- Spring ↔ AWS 서울 RDS PostgreSQL/pgvector: 씬, GT, 검색 벡터, 작업, 라벨·수정 이력.
- 로그인은 Cognito OIDC + oauth2-proxy. 현재 터널을 Cloudflare로 그리지 않는다.

**5장. 왜 전체 AWS 대신 이 구성을 선택했는가**
- 목표는 팀 시연용 MVP. 보유 GPU를 활용하면서 공유 웹 주소와 PC 재설치에 독립적인 원본·DB를 유지하려고 선택했다.
- 전체 AWS / 현재 하이브리드 / 전체 로컬을 작은 표로 비교: 비용 항목, PC 의존성, 네트워크 왕복, 운영 복잡도.
- 하이브리드는 PC·집 회선·터널 의존성이 생겼다. 24시간 운영이나 고가용성을 달성한 구조가 아니다. RDS도 소규모 단독 시연에서 반드시 필요한 것은 아니며 원격 영속 DB라는 선택의 대가가 있다.

**6장. 어떤 비용이 줄고 어떤 비용이 남는가**
- 현재 AWS compute를 운영하지 않으므로 해당 EC2/ECS/EKS 실행 비용을 피한다. 보유 GPU도 전기·장비·운영 비용이 있으므로 무료라고 쓰지 않는다.
- RDS 인스턴스·스토리지·백업, S3 저장·요청·전송, Vercel/터널 플랜, Cognito 등 실제 사용 항목은 남는다. 과거 ECR·스냅샷 등 보존 리소스 비용은 별도일 수 있다.
- 설정 기록상 RDS는 서울 `db.t4g.small`, Single-AZ, 20GiB gp3다. 최신 리소스 조회가 없으면 ‘설정 기록 기준’이라고 표시한다.
- **실제 청구액·정확한 월 절감액은 확인하지 않았다.** 금액을 넣을 경우 AWS 서울 공식 단가·확인 날짜·가동시간을 명시한 ‘예상 비용’으로만 계산한다. 월 40시간 시연 / 730시간 상시 운영은 가정이며 실제 사용량이 아니다. 크레딧·무료 구간·세금·환율도 구분한다. 확인 불가하면 금액 대신 비용 항목 표를 사용한다.
- RDS는 PC를 꺼도 자동으로 꺼지지 않는다. S3는 켜고 끄는 서버 인스턴스가 아니다.

**7장. 통신·인증·백엔드는 이렇게 연결된다**
- 브라우저의 `/api`는 Vercel과 터널을 거쳐 로컬 Spring으로 전달된다. 현재 파일은 4,000,000바이트 조각을 순서대로 보내며, 브라우저→S3 직접 업로드는 아직 아니다.
- Spring이 검증·압축 해제 → S3 보관 → RDS 등록을 담당하고, FastAPI는 모델 연산을 담당한다. 이미지 경로와 작은 요청을 전달하며 로컬 캐시를 재사용한다.
- Cognito의 JWT/OIDC, oauth2-proxy의 브라우저 세션 쿠키는 역할이 다르다. Cloudflare 전환 시 이전 Microsoft 터널 전용 연결 토큰 전달은 제거했다. RDS는 PC IP /32 접근 제한과 TLS 검증을 사용한다.
- DB 접근은 일반 조회·문서의 JPA, 대량 import의 JDBC batch, 작업·검색 등의 명시 SQL을 혼용한다. 자체 JWT 필터나 Redis 세션을 구현했다고 쓰지 않는다.

**8장. 실제 업로드 병목은 DB보다 전송 경로에 있었다**
2026-11-12 사용자가 공개 Vercel 경로로 4,168,148,189바이트 TGZ를 올린 한 번의 실측:
- 브라우저 전송 714.380초(11분 54초), 등록 대기 214.762초, 전체 929.142초(15분 29초). 검색 임베딩은 이 시간에서 제외.
- 서버 등록 내부: 복사 10.143초, 해제·검증 51.848초, S3 보관 141.499초, RDS 등록 9.921초.
- 전송이 사용자 전체 대기의 약 76.9%, S3가 등록 작업의 약 66.3%. 전체 시간과 내부 단계를 더해서 중복 계산하지 않는다.
- 1,043개 조각의 서버 처리 합은 307.103초. 전송 714.380초와의 차이 407.277초에는 조각 사이 대기·왕복·프록시·서버 진입 전 시간이 섞인다. 전부 순수 네트워크 지연으로 단정하지 않는다.

**9장. GPU 문제도 ‘계산’과 ‘대기’를 나눠 확인했다**
- CLIP은 CUDA로 실행됐다. 그러나 이미지별 순차 호출, 이미지별 DB 저장, 최대 8장 처리 후 기본 1초 대기 구조다. 8장 묶음 GPU 추론은 아니다.
- 2,208/2,424장에서 라벨 작업 #7이 먼저 실행되어 임베딩이 대기했다. #7을 중단한 뒤 남은 이미지를 처리해 2,424장 완료를 확인했다. 이후 ‘임베딩 완료 후 수동 라벨링’을 UI와 API에서 검사하도록 수정·검증·배포했다. 인덱스 완료가 라벨 작업을 자동 생성하지 않는다.
- 임베딩 첫 저장→마지막 저장은 865.306초(약 14분 25초), 라벨 작업 개입으로 약 299초의 긴 이미지 사이 공백이 포함된다. 전체 AI 호출 합 147.559초, DB 저장 호출 합 25.185초다. AI 호출 시간에는 전처리·통신 등이 포함되므로 GPU 커널 시간이라고 쓰지 않는다.
- VESPA는 Grounding DINO → SAM → LiDAR 결합·추적·3D 후처리를 거친다. 현재 후보 10개를 클래스별로 반복 평가하는 경로가 있어 같은 이미지의 중복 연산을 줄일 필요가 있다. GPU 점유율만 보고 DB나 GPU 하나를 원인으로 지목하지 않는다.

**10장. 개선 우선순위와 검증 계획**
- 전송: 같은 파일의 loopback/공개 경로 대조 → 제한된 병렬 전송 또는 S3 multipart 설계. 현재 연속 offset·재개·중복 방지 계약을 지켜야 한다.
- 연산: CLIP 묶음 추론·DB batch, Grounding DINO 이미지 특징 재사용, 모델 상주와 캐시. 단순 스레드 증가는 우선 해법으로 삼지 않는다.
- 품질을 바꾸는 대안: YOLO 기반 검출/분할을 별도 빠른 모드로 비교할 수 있으나, 클래스 범위·마스크·3D 정확도와 기존 VESPA의 차이를 검증해야 한다. Ultralytics 2D FPS를 이 파이프라인 전체 시간과 직접 비교하지 않는다.
- 결론: ‘클라우드를 나눠서 빨라졌다’가 아니라, **실행 위치를 선택하고 단계별 로그로 병목을 구분해 다음 개선 대상을 찾았다**는 것이 이번 엔지니어링 성과다.

표현 규칙:
- 현재 구조와 종료한 AWS 구조를 섞지 마. 현재 로컬 GPU가 L4라고 쓰지 마.
- ‘관측한 값 / 코드로 확인한 사실 / 개선 후보 / 미검증’을 구분해.
- 완료 결과 조회는 GPU 재실행이 아니며, 새로운 라벨 작업을 자동 시작하지 않아.
- #8·#9·#10·#11은 사용자 요청으로 중단했으므로 완료 성능 자료에서 제외해. #11 중단 후 running/pending 0, GPU 사용률 0%의 한 시점과 수동 실행 준비 상태를 확인했다. 이는 전체 모델의 GPU 상주를 증명하지 않는다.
- 모든 결과가 S3에 저장된다고 쓰지 마. RRD·후처리 파일은 현재 로컬 볼륨이고 라벨·수정은 RDS야.
- 계정 번호, 토큰, 비밀번호, 원본 센서 파일은 발표 자료에 넣지 마.
- 슬라이드 10장 이후 예상 질문 5개와 짧은 답변을 별도 메모로 작성해. 요금 출처: https://aws.amazon.com/rds/postgresql/pricing/ , https://aws.amazon.com/s3/pricing/ , https://vercel.com/pricing .
